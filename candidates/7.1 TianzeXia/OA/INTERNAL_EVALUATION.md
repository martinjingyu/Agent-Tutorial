# 内部评估指南 — 科研文献证据链审计 Agent

> **注意**：本文档为内部评估指南，仅供面试官/评估者使用，不向候选人公开。

## 一、题目总览

### 1.1 题目名称
科研文献证据链审计 Agent（Research Evidence Chain Auditor）

### 1.2 核心考察意图
本题的核心不是考察候选人写算法或调 Prompt 的能力，而是考察其 **Agent Pipeline 设计直觉**——能否设计一个可控、可扩展、鲁棒的 Pipeline 来驾驭 LLM 的三大核心缺陷（幻觉、格式漂移、信息冲突）。

### 1.3 三段式递进逻辑

| 段位 | 核心挑战 | 分值 | 设计意图 |
|------|---------|------|---------|
| 第一段：基础闭环 | 从 3 种异构源中提取声明、跨源对齐、检测矛盾 | 40 分 | 考察 Pipeline 完整性和格式鲁棒性 |
| 第二段：动态泛化 | 扩展支持 2 种新源类型，检测并消解跨源冲突 | 35 分 | 考察可扩展性设计和冲突处理能力 |
| 第三段：极限压测 | 处理损坏/恶意输入，优雅降级 | 25 分 | 考察错误恢复和鲁棒性设计 |

### 1.4 分值权重策略
- **Pipeline 设计直觉**（39 分，占 39%）：这是本题的核心分值，考察候选人对 Agent Pipeline 架构的理解
- **格式处理能力**（10 分）：考察工程实现能力
- **幻觉控制**（8 分）：考察对 LLM 缺陷的认知
- **冲突处理**（10 分）：考察跨源信息整合能力
- **鲁棒性**（25 分）：考察工程健壮性

## 二、各段标准答案/参考实现要点

### 2.1 第一段：基础闭环（40 分）

#### 2.1.1 Pipeline 架构参考

```
materials/ → [ParserRegistry] → [ClaimExtractor] → [CrossSourceAligner] → [ConflictDetector] → [Verifier] → [ReportGenerator] → stage1_report.json
```

**关键设计决策**：
1. **解析器注册机制**：使用工厂模式或注册表，每种源类型对应一个解析器类，统一 `BaseParser` 接口
2. **声明提取**：从解析结果中提取事实性陈述（数值声明、方法声明、引用声明、排名声明）
3. **跨源对齐**：按主题/实体/数值进行匹配，将相同主题的声明归入同一对齐组
4. **矛盾检测**：在对齐组内检测数值不一致、术语不统一等问题
5. **验证**：通过数值计算、引用格式检查、跨源比对等方式验证声明

#### 2.1.2 三种源解析要点

**PDF 解析**：
- 使用 PyMuPDF (fitz) 提取文本和表格
- 表格数据需要单独提取（`fitz.Table` 或正则匹配），不能只提取纯文本
- 需要区分正文中的数值和表格中的数值
- 跨页表格需要合并处理

**HTML 解析**：
- 使用 BeautifulSoup 或 lxml 去除标签
- 提取标题层级结构（h1-h6）
- 提取代码块内容（`<pre><code>` 或 `<code>`）
- 处理 HTML 实体（`&amp;` → `&`）

**CSV 解析**：
- 使用 pandas 或 csv 模块
- 自动检测分隔符（逗号、制表符、分号）
- 处理引号转义和换行
- 统一数值格式（百分比 → 小数）

#### 2.1.3 植入噪声的预期检测方式

| 噪声类型 | 植入位置 | 预期检测方式 |
|---------|---------|-------------|
| **数值矛盾** | 论文正文 vs 表格 | 提取正文和表格中的数值，对比同一指标的值 |
| **引用幻觉** | 参考文献中无效 DOI | 检查 DOI 格式（`10.xxxx/xxxx`），尝试解析 |
| **格式漂移** | CSV 中 % 与小数混用 | 检测数值格式，统一转换为小数 |
| **术语不一致** | 不同源对同一概念使用不同术语 | 构建同义词表或使用语义相似度匹配 |

#### 2.1.4 脚手架缺陷及预期修复方式

| # | 缺陷位置 | 缺陷描述 | 预期修复方式 |
|---|---------|---------|-------------|
| 1 | `parsers.py` | PDF 解析器忽略表格数据，只提取正文文本 | 添加表格提取逻辑，使用 `page.get_tables()` 或正则匹配 |
| 2 | `schema.py` | JSON Schema 缺少 `conflicts` 字段 | 在 `aligned_groups` 中添加 `conflicts` 数组 |
| 3 | `llm_client.py` | 无超时重试机制，LLM 调用失败直接崩溃 | 添加指数退避重试逻辑和超时设置 |
| 4 | `pipeline.py` | 硬编码源文件路径 | 使用配置参数或命令行参数传入路径 |
| 5 | `utils.py` | 缺少数值归一化函数 | 添加 `normalize_number()` 函数处理百分比/小数转换 |
| 6 | `parsers.py` | CSV 解析器不处理引号转义 | 使用 `csv.reader` 或 pandas 的正确参数 |

### 2.2 第二段：动态泛化（35 分）

#### 2.2.1 新增源解析要点

**会议演讲转录文本**：
- 去除时间戳标记（`[00:12:34]`）
- 处理口语化表达（口误、重复、自我纠正）
- 识别演讲者可能的口误（如说"87.5"但实际应为"78.5"）

**Reddit 讨论帖**：
- 解析 JSON 结构，提取帖子正文和评论
- 区分不同评论者的观点
- 识别未经证实的"内部消息"或主观判断

#### 2.2.2 植入冲突的预期检测方式

| 冲突类型 | 植入位置 | 预期检测方式 |
|---------|---------|-------------|
| **数值冲突** | 转录文本中口误导致数值错误 | 跨源比对，发现转录文本中的数值与论文/CSV 不一致 |
| **主张冲突** | 博客夸张表述 vs 论文数据 | 检测博客中的"彻底解决""革命性"等关键词，与论文数据对比 |
| **排名冲突** | Benchmark vs 社交媒体 | 对比 CSV 中的方法排名与 Reddit 讨论中的评价 |
| **时序矛盾** | 转录文本说"放弃了方法 A"但论文仍推荐方法 A | 检测同一方法在不同源中的状态描述矛盾 |

#### 2.2.3 可信度评分参考模型

```
confidence = w1 * authority_score + w2 * consistency_score + w3 * recency_score

其中：
- authority_score: 论文=0.9, 技术博客=0.7, CSV=0.8, 转录文本=0.5, Reddit=0.3
- consistency_score: 跨源一致数量 / 总源数量
- recency_score: 较新的数据权重更高
- w1=0.4, w2=0.4, w3=0.2 (可调整)
```

### 2.3 第三段：极限压测（25 分）

#### 2.3.1 异常输入处理要点

**损坏 PDF（20-30% 不可读）**：
- 使用 try-except 包裹每页解析，失败页跳过
- 记录损坏页码和损坏类型
- 提取可读部分的内容

**恶意噪声 CSV**：
- NaN/None/Null → 转换为空值或标记
- SQL 注入语句 → 检测 `DROP`、`SELECT`、`INSERT` 等关键词，转义或过滤
- 格式异常 → 使用 `error_bad_lines=False` 或自定义行解析器

**LLM 伪造文本**：
- 检测虚构的论文标题（与已知论文库对比）
- 检测不存在的基准分数（超出正常范围）
- 检测错误的引用格式

#### 2.3.2 降级策略参考

```
def process_with_degradation(source_list, max_failures=2):
    successful = []
    failed = []
    for source in source_list:
        try:
            result = process_source(source)
            successful.append(result)
        except Exception as e:
            failed.append({"source": source, "error": str(e)})
            if len(failed) > max_failures:
                log.warning(f"超过最大失败数 {max_failures}，继续处理剩余源")
    return successful, failed
```

## 四、加分项判断标准（上限 +10 分）

### 4.1 主动重构脚手架代码（+3 分）

**判断标准**：
- 候选人发现并修复了脚手架中的缺陷
- 修复方式合理，不引入新问题
- 在代码注释或架构文档中说明了修复原因

**评分操作**：
- 对比原始脚手架代码和候选人提交的代码
- 检查是否修复了以下缺陷：
  1. PDF 解析器忽略表格数据
  2. Schema 缺少 conflicts 字段
  3. LLM 客户端无超时重试
  4. 硬编码路径
  5. 缺少数值归一化
  6. CSV 解析不处理引号转义

### 4.2 可视化方案（+2 分）

**判断标准**：
- 生成了有意义的可视化图表
- 图表与报告内容关联（如冲突热力图、证据链图、可信度仪表盘）
- 可视化代码可独立运行

### 4.3 缓存机制（+2 分）

**判断标准**：
- 实现了文件级或声明级的缓存
- 缓存支持增量更新（只重新处理变更的文件）
- 缓存有过期机制或手动清除方式

### 4.4 单元测试（+2 分）

**判断标准**：
- 测试覆盖核心模块（解析器、冲突检测、Schema 校验）
- 测试用例覆盖正常路径和异常路径
- 测试可自动运行（如 `pytest`）

### 4.5 创新方案（+1 分）

**判断标准**：
- 超出题目要求的额外设计
- 设计有实际价值，非过度工程
- 示例：自动修复建议、交互式报告、多语言支持

## 五、扣分项判断标准

### 5.1 硬编码路径（-3 分）

**判断标准**：
- 代码中出现 `C:/`、`/home/`、`/Users/` 等绝对路径
- 未使用 `os.path.join()` 构建路径
- 路径未通过参数或配置传入

### 5.2 吞异常（-3 分）

**判断标准**：
- 出现空的 `except:` 或 `except Exception: pass`
- 异常被捕获后未记录日志或做有意义的处理
- 异常信息丢失

### 5.3 过度工程（-2 分）

**判断标准**：
- 使用了不必要的设计模式（如为 3 个解析器引入抽象工厂）
- 过度抽象导致代码难以理解
- 冗余代码（如多个功能重复的函数）

### 5.4 LLM 过度依赖（-3 分）

**判断标准**：
- 将数值计算交给 LLM 而非代码实现
- 将格式校验交给 LLM 而非代码实现
- LLM 调用失败导致核心功能不可用

## 六、常见候选人策略分析

### 6.1 预期策略分布

| 策略类型 | 预期比例 | 典型特征 | 评分倾向 |
|---------|---------|---------|---------|
| **工程稳健型** | 40% | 代码结构清晰、异常处理完善、模块化好 | 中高分 |
| **算法创新型** | 25% | 在冲突检测或可信度评分上有独特方法 | 中高分（加分项） |
| **快速完成型** | 20% | 优先保证链路完整，代码质量一般 | 中等分数 |
| **过度设计型** | 10% | 使用了过多设计模式，核心功能反而薄弱 | 中低分 |
| **LLM 依赖型** | 5% | 大量依赖 LLM 完成核心逻辑 | 低分 |

### 6.2 常见失误

1. **时间管理失败**：第一段花费超过 2.5 小时，导致第二、三段仓促完成
2. **忽略表格数据**：PDF 解析器只提取正文文本，遗漏表格中的数值
3. **硬编码路径**：在代码中写死材料路径，无法在不同环境运行
4. **JSON Schema 不符合**：输出缺少必填字段或字段类型错误
5. **冲突检测遗漏**：第二段未检测到植入的跨源冲突
6. **降级策略缺失**：第三段遇到损坏输入直接崩溃
7. **LLM 过度依赖**：将数值计算和格式校验交给 LLM

### 6.3 高分候选人特征

1. **Pipeline 完整闭环**：采集→解析→对齐→检测→验证→报告全链路覆盖
2. **可扩展架构**：新增源类型只需添加一个解析器类
3. **冲突检测全面**：检测到 3 处以上跨源冲突，分类清晰
4. **鲁棒性强**：损坏输入不崩溃，优雅降级
5. **代码质量高**：模块化清晰、命名规范、有类型注解
6. **加分项完成**：修复脚手架缺陷、单元测试、可视化

## 九、评估注意事项

### 9.1 评分原则

1. **Pipeline 设计直觉优先**：39 分的 Pipeline 设计分值是最核心的，应优先评估
2. **功能完整性 > 代码优雅性**：能跑通完整链路的 Pipeline 优于代码漂亮但功能残缺的
3. **加分项是锦上添花**：加分项不应弥补基础功能的缺失
4. **扣分项严格执行**：硬编码路径、吞异常等是工程红线

### 9.2 常见评分争议处理

| 争议场景 | 处理建议 |
|---------|---------|
| 候选人使用了非 Python 语言 | 如果功能完整，不扣分；但需确认环境要求是否满足 |
| 候选人使用了 Agent 框架（如 LangChain） | 不扣分，但需评估候选人是否理解底层原理 |
| 候选人提交了部分功能 | 按已完成部分评分，未完成部分记 0 分 |
| 候选人超时提交 | 按评分标准正常评分，记录超时情况供参考 |
