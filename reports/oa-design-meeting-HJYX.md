- **暴露夸大最有效**：GRPO/RL/vLLM/DeepSpeed 在本题无自然落脚点，强行塞入暴露不懂
- **防背题能力最强**：陌生场景，候选人无法提前准备
- **贴合 JD 最紧密**：JD 强调"多种类垂直AI协作"和"非结构化信息结构化"

**吸收 B 的 QA 方法论**：采用赵雷的"可量化检查表 + 档位判定"双层评分结构，确保评判一致性。

## 议题 2：题目难度与陷阱设计

### 分阶段递进设计（确保无法 One-Shot）

| 阶段 | 时长 | 输入 | 要求 | 陷阱 |
|------|:----:|------|------|------|
| **Stage 1：基础融合** | 20min | 3 个情报源（2 JSON + 1 纯文本） | 输出结构化融合报告 | 数值冲突（10 vs 50 vs "数十人"），纯文本无时间戳 |
| **Stage 2：增量更新** | 15min | 追加第 4-5 个情报源 | 更新融合报告，标记变更 | 需要版本管理 + 冲突标记 |
| **Stage 3：置信度加权** | 15min | 给每个源标注可信度（0.4~0.9） | 重新计算融合结果置信度 | 需要加权融合算法 |
| **Stage 4：架构追问** | 10min | 口头追问 | 分析扩展到 30 个源的瓶颈 | 暴露 GRPO/RL/vLLM/DeepSpeed 是否真懂 |

### 7 类噪声/冲突/缺失信息

| # | 类型 | 具体设计 | 对应情报源 |
|---|------|---------|-----------|
| ① | **数值冲突** | 死亡人数：10 vs 50 vs "几十个" vs 12 | 源 A/B/C/D |
| ② | **时间冲突** | 14:30 vs 15:10 vs 无时间 vs 次日 08:00 | 源 A/B/C/D |
| ③ | **实体别名** | "化工园区" vs "上海化工区" vs "上海化学工业区" | 源 A/B/C |
| ④ | **精度缺失** | 源 B 缺少经纬度，源 C 缺少时间/精确数字 | 源 B/C |
| ⑤ | **格式噪声** | 源 C 含 #话题标签、口语化表达 | 源 C |
| ⑥ | **可信度差异** | 0.4~0.9 不等 | 所有源 |
| ⑦ | **过时信息** | 源 A/B 是初步报告，源 D 是最终报告 | 源 A/B vs D |

### 8 个故意代码缺陷

| # | 缺陷 | 代码表现 | 检测方式 | 打击目标 |
|---|------|---------|---------|---------|
| ① | **无错误处理** | `fetch_source()` 无 try-except，无 timeout | 搜索 `try` | 错误处理 |
| ② | **无重试机制** | LLM 调用失败直接退出 | 搜索 `retry` / `while` | 验证重试 |
| ③ | **无冲突检测** | `merge_reports()` 直接 `dict.update()` 覆盖 | 搜索 `conflict` / `resolve` | 信息冲突处理 |
| ④ | **无格式校验** | `parse_article()` 假设输入总是有效 JSON/HTML | 搜索 `isinstance` / `try` | 异常处理 |
| ⑤ | **Prompt 硬编码** | 所有 LLM 调用用同一个固定 prompt | 检查 prompt 是否动态构建 | Prompt Engineering |
| ⑥ | **无上下文管理** | `self.history` 无限增长 | 搜索 `token` / `window` / `summary` | 上下文管理 |
| ⑦ | **配置硬编码** | API key、model name 等硬编码在代码中 | 搜索环境变量/配置文件 | 工程化落地 |
| ⑧ | **单线程串行** | 串行处理所有源，无并行 | 搜索 `async` / `ThreadPool` | 工程化落地 |

## 议题 3：模块划分

### 题包文件结构（17 个文件）

```
oa-package/
├── README.md                          # 题目总说明（场景描述、分阶段要求、交付物清单）
├── CONTEXT.md                         # 领域知识包（术语表 + 流程图 + Mini Example）
├── DELIVERABLES.md                    # 交付物清单（明确候选人需要提交什么）
├── SCORING.md                         # 评分标准（面试官用）
├── qa_checklist.md                    # QA 逐项核对清单（面试官评分时逐项打勾）
├── materials/
│   ├── phase1/                        # Phase 1 材料（基础融合）
│   │   ├── source_a.json              # 官方通报，结构化 JSON，伤亡 10/45
│   │   ├── source_b.json              # 社交媒体汇总，JSON（缺经纬度），伤亡 50/200
│   │   └── source_c.txt               # 个人博客，纯文本（含噪声），模糊表述
│   └── phase2/                        # Phase 2 材料（增量更新）
│       ├── source_d.json              # 内部讨论，低可信度(0.3)，伤亡 5/20
│       └── source_e.json              # 官方最终通报，高可信度(0.9)，伤亡 12/52
├── scaffold/                          # 半成品代码
│   ├── main.py                        # Pipeline 主流程（无日志、无验证、单线程串行）
│   ├── config.py                      # 配置管理（故意留空，让候选人补充）
│   ├── fetcher.py                     # 情报采集模块（无 timeout、无异常捕获、无重试）
│   ├── parser.py                      # 情报解析模块（假设输入总是有效 JSON/HTML）
│   ├── fusion.py                      # 情报融合模块（直接覆盖、无冲突检测、无上下文管理）
│   ├── reporter.py                    # 报告生成模块（Prompt 硬编码、无结构化输出）
│   ├── models.py                      # 数据模型定义（故意留空，只有注释）
│   └── requirements.txt               # 依赖声明（openai, pydantic, requests）
└── tests/
    ├── sample_output.json             # 期望输出格式示例
    └── qa_baseline.py                 # One-Shot baseline 验证脚本
```

### 降档机制

```
如果候选人简历声称 ≥ 3 项高级技能（GRPO/RL/vLLM/DeepSpeed/多Agent编排）
但代码中：
  - 无错误处理 → 扣 25%
  - 无重试机制 → 扣 10%
  - Prompt 硬编码 → 扣 15%
  - 无冲突检测 → 扣 10%
  - 总分 < 40 → 直接标记为"简历夸大，建议拒绝"
```
