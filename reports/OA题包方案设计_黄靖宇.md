## 二、业务场景选择

**最终方案：以"Agent安全审计"为核心场景，融入对抗元素**

三位专家一致认为，场景应结合候选人的Red-Teaming背景与JD的Agent方向要求。最终选择"Agent安全审计"场景，理由：

1. **衔接候选人背景**：安全审计天然涉及对抗思维，让候选人发挥Red-Teaming优势
2. **覆盖JD要求**：Agent架构搭建、Agent Loop优化、LLM API调用、Prompt工程全覆盖
3. **复杂度可分层**：从单源审计到多Agent协作，天然支持三段式演进
4. **弱点暴露充分**：工程健壮性在审计场景中至关重要（不能漏判、不能崩溃）

## 三、三道题详细设计

### 第一题：「哨兵Agent：基于安全策略的LLM输出审计器」（基础闭环）

| 项目 | 内容 |
|------|------|
| **考察点** | Agent Loop设计、LLM API调用、Pipeline设计、Prompt Engineering基础、代码组织能力 |
| **输入** | 约20000字 raw material（含干扰文档），20条混合内容（安全/违规/边界/格式异常） |
| **输出** | 结构化JSON：summary + details（每条内容判定）+ meta（token/耗时/错误） |
| **难度梯度** | 基础(必做60min)→进阶(选做30min, batching/并发/成本统计)→挑战(选做30min, 策略热加载/缓存) |
| **预期通过率** | 基础70%, 进阶40%, 挑战20% |

**噪声/干扰项设计：**
- `irrelevant_policies.pdf`：完全不相关的物理安全策略，含"审计"关键词误导
- `old_audit_results.json`：旧格式审计结果，字段不同，考察是否仔细阅读规范
- `api_docs.md`：OpenAI API文档节选，含误导性参数建议（temperature=0.7）
- `meeting_notes.txt`：团队周会记录，含"审计"关键词但无关

**脚手架故意缺陷（8个，分三层）：**

| 层级 | 缺陷 | 位置 | 分值 |
|------|------|------|------|
| L1 | 空值/空内容崩溃 | `AuditAgent.run()` | 10 |
| L1 | LLM API调用无重试 | `_audit_single()` | 10 |
| L1 | Prompt无系统消息/无格式约束 | `_build_prompt()` | 15 |
| L2 | 策略加载无校验/无缓存 | `policy_loader.py` | 8 |
| L2 | 并发处理无锁/无速率限制 | `run_concurrent()` | 8 |
| L2 | 审计结果聚合逻辑错误 | `AuditAggregator` | 5 |
| L3 | Token成本估算完全缺失 | 全局 | 12 |
| L3 | 完全依赖LLM，无规则引擎兜底 | `_audit_single()` | 15 |

### 第二题：「变异哨兵：基于自进化策略的未知威胁检测Agent」（动态泛化）

| 项目 | 内容 |
|------|------|
| **考察点** | Agent框架自适应能力、Prompt Engineering深度、LLM高级调用模式(Function Calling)、异常检测与泛化、自进化机制 |
| **输入** | 第一题输出 + 新增变异内容（绕过固定策略的对抗样本）+ 历史审计日志 |
| **输出** | 自进化轨迹 + 新策略集 + 重新审计结果 + 进化效果评估 |
| **难度梯度** | 基础(必做45min, 检测漏报+分析模式)→核心(必做45min, 策略生成+验证+合并)→进阶(选做30min, 策略冲突检测+回滚) |
| **预期通过率** | 基础60%, 核心35%, 进阶15% |

**核心机制设计：**
1. **检测漏报**：用第一题的Agent审计变异内容，识别漏报
2. **模式分析**：对漏报内容做聚类，提取共同模式
3. **策略生成**：基于模式用LLM生成新策略（Function Calling结构化输出）
4. **验证门控**：在benign样本上验证新策略误报率
5. **策略合并**：新策略与旧策略合并，检测冲突
6. **迭代终止**：基于检测率提升幅度自动终止

**简历夸大陷阱：**
- 在题目说明中埋入"可选加分项：如果你熟悉GRPO/RL，可以设计Reward Model优化Agent"
- 真正用过GRPO的人会知道需要多采样对比+KL散度约束
- 如果只实现简单规则Reward → 简历夸大嫌疑

### 第三题：「分布式哨兵集群：海量异构数据流审计架构」（极限压测 — 面试讨论环节）

| 项目 | 内容 |
|------|------|
| **考察点** | 分布式架构设计、Master-Worker调度、背压机制、成本感知调度、Checkpoint恢复、容错设计 |
| **场景** | 100万条/30分钟数据流，4个异构数据源，$100预算，3次延迟spike |
| **输出** | 架构设计方案（文字+架构图）+ 核心Worker实现 + 性能/成本/可靠性指标 |
| **难度梯度** | 基础(必做45min, 架构设计)→核心(必做60min, Master-Worker实现)→进阶(选做30min, 背压/优先级)→挑战(选做30min, 成本感知调度/Checkpoint) |
| **预期通过率** | 基础50%, 核心25%, 进阶10% |

**架构陷阱设计：**
1. **Master-Worker vs 去中心化**：题目暗示Master-Worker，真正有经验的架构师会质疑
2. **任务分片**：4个数据源吞吐量差异达100倍，平均分片暴露数据敏感性不足
3. **LLM调用策略**：$100预算100万条数据，每条成本上限$0.0001，必须用规则引擎预筛
4. **状态管理**：有状态Worker崩溃丢数据 vs 无状态+外部存储
5. **延迟spike处理**：3次spike（5x/10x/20x），需要自适应背压+熔断+降级

## 五、面试追问清单

### 针对"自进化Agent框架"的追问链

```
Q1: 单机自进化 → 8个Worker集群，每个Worker独立进化还是全局共享？
  → 独立进化：策略冲突怎么解决？
  → 全局共享：更新频率？原子性？
  → 混合：划分边界规则？

Q2: 自进化每次迭代调LLM，$100预算能迭代几次？
  → 固定次数：遇到新型攻击怎么办？
  → 动态调整：进化成本vs收益的trade-off？

Q3: 自动生成策略的可解释性？
  → 记录推理过程：LLM生成的可能含幻觉
  → 人工审核：每天100万条，价值在哪？
```

## 七、总结

本OA方案围绕"Agent安全审计"场景，采用三段式演进（基础闭环→动态泛化→极限压测），针对候选人Jingyu Huang的特点：

- **利用强项**：Agent框架设计能力在第二题（自进化）和第三题（分布式架构）中充分考察
- **暴露弱点**：工程健壮性通过8个脚手架缺陷精准考核，Prompt Engineering通过简陋prompt暗桩验证
- **验证简历**：GRPO/RL/vLLM/DeepSpeed等技术栈通过可选加分项和面试追问链验证
- **区分度设计**：第一题70%通过率保底，第三题10%通过率筛选顶尖

**建议出题负责人**：按照本方案中的三道题详细设计、脚手架缺陷代码、评分体系、面试追问清单，准备完整的OA题包文件。
