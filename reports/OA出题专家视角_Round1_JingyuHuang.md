## 1. 主题选择：「跨源事实核验 Pipeline」是否合适？

### 总体判断：方向正确，但需要微调

**合适之处**：
- ✅ **打击弱点精准**：Jingyu 上次 OA 的弱项是"零错误处理、Prompt 深度不足、无测试覆盖"。跨源事实核验天然需要错误处理（LLM 输出不可靠）、动态 Prompt（不同来源不同提取策略）、验证闭环（Checker 检测幻觉）—— 正好打在弱点上。
- ✅ **防背题能力强**：这不是 LeetCode 题，也不是常见的 RAG/QA 题。候选人无法提前准备标准答案。
- ✅ **贴合 JD 核心**：JD 要求"Agent Pipeline 搭建与优化"、"Loop 与性能优化"、"大模型 API 调用与 Prompt 工程"—— 本题全部覆盖。

**需要微调之处**：
- ⚠️ **"跨源事实核验"这个名字太学术化**，容易让候选人联想到 FactCheck 论文（如 FEVER、SciFact），从而套用论文中的方法（如 entailment classification），偏离了我们想考察的 Pipeline 设计能力。建议改为更工程化的名字，如 **「多源情报质量门禁 Pipeline」** 或 **「异构数据融合与自修正系统」**。
- ⚠️ **业务场景需要更"痛"**：目前的"新闻聚合平台 FactFlow"场景虽然合理，但痛点不够尖锐。建议改为一个**有明确业务后果**的场景，比如"金融合规报告自动生成"—— 如果 LLM 幻觉导致合规报告出错，公司会被罚款。这样候选人对"为什么需要 Checker"、"为什么需要置信度"的理解会更深刻。

### 有没有更好的主题方向？

我评估了三个候选方向：

| 方向 | 打击弱点 | 验证强项 | 暴露夸大 | 贴合 JD | 总分 |
|------|:--------:|:--------:|:--------:|:-------:|:----:|
| **A. 跨源事实核验**（当前方案） | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ | **16/20** |
| **B. 质量门禁 + 自修正**（上次会议方案） | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | **19/20** |
| **C. 安全审计情报融合**（另一版方案） | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐ | **15/20** |

**我的推荐：方案 B（质量门禁 + 自修正）> 方案 A（跨源事实核验）**

理由：
1. **"质量门禁"这个比喻更工程化**，候选人不会往学术论文方向跑偏
2. **"自修正"天然引出循环机制**，这是考察 Test-Time Compute 和 Loop 设计的最佳载体
3. **与 Jingyu 的 Linksome 经验衔接更自然**—— Linksome 做的就是多 Agent 输出质量控制，他能快速进入状态，但也会暴露他是否真的理解质量控制背后的原理（而非只是调过 API）

## 2. 业务场景：新闻核验 vs 金融数据对齐 vs 其他？

### 我的建议：金融合规报告自动生成

| 场景 | 优势 | 劣势 |
|------|------|------|
| **新闻核验** | 候选人容易理解，材料容易构造 | 太像 FactCheck 论文题，容易套用现成方法 |
| **金融数据对齐** | 痛点尖锐（合规罚款），数值精度要求高，天然需要置信度 | 需要一定金融背景知识 |
| **安全审计** | 与 Jingyu 红队背景衔接 | 场景太窄，JD 不要求安全背景 |
| **医疗报告核验** | 痛点尖锐（人命关天） | 需要医学知识，候选人可能不熟悉 |

**推荐场景：金融合规报告自动生成**

具体设定：
> 你所在的 FinReport 平台每天自动生成上市公司财报摘要。平台用 LLM 从 SEC Filing、新闻稿、分析师报告、社交媒体中提取关键财务数据。但运营团队发现 LLM 经常"脑补"财务数字、混淆 QoQ/YoY 增长率、把不同季度的数据混在一起。你的任务是设计一个质量门禁 Pipeline，对 LLM 输出进行交叉验证、幻觉检测、格式修复，确保最终报告符合 SEC 合规要求。

**为什么选这个场景**：
1. **数值精度要求高** — 财务数据差一个零就是百万 vs 亿的差距，天然需要高置信度阈值
2. **冲突类型丰富** — 同一营收数据在不同来源中可能因 GAAP vs Non-GAAP 口径不同而不同
3. **时序敏感** — Q1/Q2/Q3 数据不能混淆，考察时序错乱检测
4. **业务后果明确** — 合规报告出错 = 罚款，候选人能理解"为什么需要 Checker"

## 3. 三段式结构：每个阶段应该考察什么能力？

### 我的设计框架

```
基础闭环（35%） → 动态泛化（40%） → 极限压测（25%）
    ↓                   ↓                   ↓
  确定性能力          不确定性能力        系统级能力
```

### Stage 1：基础闭环（35%）— 考察"确定性能力"

**核心问题**：给定明确的 Schema 和规则，候选人能否让 LLM 稳定输出？

**具体考察点**：

| 能力 | 考察方式 | 对应 JD |
|------|---------|---------|
| **输出格式控制** | 给定 JSON Schema，要求 LLM 输出严格符合 Schema | 大模型 API 调用与 Prompt 工程 |
| **基础错误处理** | LLM 返回非法 JSON 时能否捕获并重试 | Agent 架构搭建 |
| **简单冲突检测** | 两个来源的同一字段值不同时能否标记 | Pipeline 设计 |
| **状态传递** | Extractor → Validator → Checker 的数据流是否清晰 | Agent Workflow |

**关键设计原则**：这一阶段要**给足脚手架**，让候选人能快速跑起来。脚手架代码故意包含 5-6 个简单缺陷（无 try-except、无输出校验、硬编码 Prompt），候选人修复这些缺陷就能拿到基础分。

**验收标准**：
- ✅ Pipeline 连续运行 5 次，至少 4 次成功
- ✅ 输出 JSON 符合给定 Schema
- ✅ 检测到至少 1 处事实矛盾
- ✅ 代码可运行（`python pipeline.py` 不报错）

### Stage 2：动态泛化（40%）— 考察"不确定性能力"

**核心问题**：当 Schema 未知、事件类型未知、噪声类型未知时，候选人能否设计一个自适应框架？

**具体考察点**：

| 能力 | 考察方式 | 对应 JD |
|------|---------|---------|
| **动态 Schema 设计** | 不预定义字段，让 Pipeline 自动发现需要提取的维度 | 多种类垂直 AI 协作 |
| **冲突分级** | 区分"明确矛盾"、"疑似矛盾"、"信息互补" | Loop 与性能优化 |
| **幻觉检测** | 识别虚构事件/实体/数字 | LLM 缺陷理解 |
| **循环修正** | Checker 发现问题后能否定向修复而非整体重跑 | Test-Time Compute |
| **置信度量化** | 基于来源权威性、一致性、时效性计算置信度 | 前沿技术跟进 |

**关键设计原则**：这一阶段要**撤掉脚手架**，让候选人自己设计 Schema 和架构。输入材料从 5 条扩展到 10 条，覆盖 3 种不同事件类型，新增 2 种噪声类型。

**验收标准**：
- ✅ Pipeline 能自动识别事件类型并调整提取维度
- ✅ 冲突标记分为至少 3 个等级
- ✅ 能识别出幻觉文本并标记为"低置信度"
- ✅ 循环修正最多 5 次必须收敛，发散时能回滚

### Stage 3：极限压测（25%）— 考察"系统级能力"

**核心问题**：在资源约束（10 个 LLM 调用/事件、5 分钟处理时限、50+ 事件类型）下，候选人如何做架构取舍？

**具体考察点**：

| 能力 | 考察方式 | 对应 JD |
|------|---------|---------|
| **架构取舍** | 分块策略、去重策略、冲突解决策略的选择 | Agent 架构优化 |
| **成本意识** | LLM 调用次数预算分配 | 性能优化 |
| **可观测性** | 如何监控 Pipeline 健康状况 | 工程化落地 |
| **容错设计** | 某个组件持续失败时如何降级 | 系统设计 |
| **技术栈诚实度** | 追问 GRPO/vLLM/DeepSpeed 的具体适用性 | 诚实度验证 |

**关键设计原则**：这一阶段是**面试口述**，不是笔试。面试官通过追问来验证候选人是否真的理解自己的设计，以及是否诚实面对知识边界。

**验收标准**：
- ✅ 画出清晰的架构图（组件、数据流、存储）
- ✅ 对至少 3 个设计取舍给出明确选择并说明理由
- ✅ 指出至少 2 个可能的瓶颈和对应的缓解方案
- ✅ 对简历中声称的技术栈（GRPO/vLLM/DeepSpeed）给出诚实的使用判断

## 4. 与候选人匹配度：如何针对 Jingyu 的强弱项？

### Jingyu 的强弱项映射

| 维度 | 强/弱 | 题目如何针对 |
|------|:-----:|-------------|
| **Linksome 验证工作流** | ✅ 强 | Stage 1 的"质量门禁"场景与 Linksome 的 Agent 输出验证高度相似。但我们会**故意在脚手架中埋入 Linksome 不会遇到的坑**（如跨文档关联、版本冲突），看他是否只是"做过类似的事"还是"真正理解了原理" |
| **Agent-Tutorial 自审查** | ✅ 强 | Stage 2 的"循环修正"机制与 Agent-Tutorial 的 Guardian-Worker 自修正架构有概念重叠。追问时会深入问"你的收敛检测算法是什么？发散时怎么回滚？"—— 如果他只是抄了 Agent-Tutorial 的模式但不懂原理，会被问倒 |
| **上次 OA 的 Prompt 弱项** | ❌ 弱 | 上次 OA 评分 6.4/10，核心弱项是 Prompt 深度不足。本题中：<br>1. Stage 1 要求动态构建 Prompt（而非硬编码）<br>2. Stage 2 要求设计 Prompt 模板系统（角色模板、格式模板、事实约束模板）<br>3. 评分维度中"Prompt 工程"占 15%，且要求有正交验证 |
| **上次 OA 的零错误处理** | ❌ 弱 | 本题脚手架代码故意包含 5-6 个无错误处理的缺陷。如果候选人仍然不修复这些缺陷，直接扣 25%（错误处理维度） |
| **技术栈夸大（GRPO/RL/vLLM/DeepSpeed）** | ❌ 风险 | Stage 3 追问中专门设计了 3 个问题：<br>1. "GRPO 在这个场景中可以用在哪里？具体 reward 怎么设计？"<br>2. "vLLM Continuous Batching 能否用于优化质量门禁的吞吐？"<br>3. "DeepSpeed ZeRO 在这个场景中是否适用？"<br>如果候选人强行堆砌这些技术但说不清具体实现，直接触发诚实度扣分（-10 到 -20 分） |
| **无测试覆盖习惯** | ❌ 弱 | Stage 1 的验收标准要求"连续运行 5 次至少 4 次成功"，这本身就是一种测试。如果候选人没有写任何测试代码，扣工程化素养分 |
| **AI 辅助痕迹（初始大块提交）** | ⚠️ 存疑 | 本题的**防背题设计**（陌生场景 + 动态 Schema + 循环修正）使得 AI 辅助难以生成完整解决方案。如果候选人提交的代码结构过于完美但无法解释设计决策，面试追问时会暴露 |

### 针对性陷阱设计

| 陷阱 | 针对的弱点 | 具体设计 |
|------|-----------|---------|
| **"看起来像"陷阱** | Linksome 经验表面化 | 输入材料中包含一个"看起来像"标准冲突但实际上是不同口径（GAAP vs Non-GAAP）的数据。如果候选人直接标记为"矛盾"而不深入分析口径差异，说明对数据理解不深 |
| **"自修正死循环"陷阱** | Agent-Tutorial 模式化 | 循环修正中设置一个"永远无法收敛"的场景（Checker 每次修复都引入新问题）。看候选人是否设计了最大迭代限制和发散回滚机制 |
| **"Prompt 万能论"陷阱** | Prompt 深度不足 | 输入材料中包含一个"无论怎么调 Prompt 都无法解决"的问题（如两个来源的数值差异是因为统计口径不同而非 LLM 错误）。看候选人是否意识到"有些问题不能靠 Prompt 解决" |
| **"技术栈堆砌"陷阱** | 夸大技术栈 | Stage 3 追问中故意问"你觉得 DeepSpeed ZeRO 能用来加速你的 Checker 吗？"—— 正确答案是"不能，因为 Checker 是 LLM 调用密集型而非计算密集型，ZeRO 的梯度分片在这里没有用武之地" |

## 5. 与 JD 匹配度：如何确保考察"LLM 直觉"和 Pipeline 设计能力？

### JD 核心要求 vs 题目设计

| JD 要求 | 题目如何考察 | 确保不是纯算法 | 确保不是纯 Prompt 调优 |
|---------|-------------|:-------------:|:--------------------:|
| **Agent 架构搭建与优化** | Stage 1+2 要求设计多组件 Pipeline（Extractor → Validator → Checker → Corrector） | ✅ 不考排序/搜索/图算法，只考组件划分和数据流设计 | ✅ 不考 Prompt 模板语法，只考"什么时候该用 LLM、什么时候不该用" |
| **Loop 与性能优化（Test-Time Compute）** | Stage 2 的循环修正机制 + Stage 3 的架构取舍 | ✅ 不考时间复杂度分析，只考"如何用多次 LLM 调用换取质量提升" | ✅ 不考 Prompt 链的具体写法，只考"循环的收敛条件和回滚策略" |
| **大模型 API 调用、配置、Prompt 工程** | Stage 1 的动态 Prompt 构建 + Stage 2 的 Prompt 模板系统 | ✅ 不考 API 文档记忆，只考"如何设计 Prompt 使其在不同输入下稳定输出" | ✅ 评分看的是"Prompt 模板的泛化能力"而非"Prompt 措辞是否优美" |
| **前沿技术跟进** | Stage 3 追问中验证 GRPO/vLLM/DeepSpeed 的真实理解 | ✅ 不考论文细节记忆，只考"在什么场景下用、解决了什么问题" | ✅ 追问的是"适用性判断"而非"参数配置" |
| **加分：Multi-Agent 协作** | Stage 2 的多个专业 Agent 协作（财务 Agent、技术 Agent、合规 Agent） | ✅ 不考通信协议实现，只考"Agent 职责划分和共识机制" | ✅ 不考 Agent Prompt 模板，只考"什么时候需要多 Agent、什么时候单 Agent 就够了" |

### 评分权重的核心设计

```
Pipeline 设计直觉（40%） ← 这是核心，不是代码质量
├── 组件划分是否合理（15%）
├── 数据流设计是否清晰（15%）
└── 架构取舍是否有理有据（10%）

LLM 缺陷控制（25%）     ← 这是"LLM 直觉"的体现
├── 幻觉检测策略（10%）
├── 格式漂移控制（8%）
├── 冲突分级逻辑（7%）

代码质量（15%）          ← 允许粗糙，但要有基本错误处理
├── 错误处理（8%）
├── 模块化（4%）
├── 可读性（3%）

输出质量（20%）          ← 结果说话
├── 事实准确率（10%）
├── 格式合规率（5%）
├── 完整性（5%）
```

**关键设计决策**：
1. **40% 分值压在 Pipeline 设计直觉上** — 即使代码有 bug，只要架构设计合理，也能拿到大部分分数
2. **"LLM 缺陷控制"占 25%** — 这是区分"调 API 的"和"真正理解 LLM 的"的关键维度
3. **代码质量只占 15%** — 允许候选人用伪代码或简化实现，不要求生产级代码
4. **没有"Prompt 措辞"评分项** — 不考察 Prompt 是否写得"漂亮"，只考察 Prompt 是否"有效"

### 防"背题"和"AI 辅助"的机制

| 机制 | 说明 |
|------|------|
| **动态输入** | 每次运行时输入材料中的噪声位置和类型随机变化，候选人无法硬编码处理逻辑 |
| **未知维度** | Stage 2 不告诉候选人需要提取哪些维度，必须自己分析 |
| **面试追问** | Stage 3 的追问无法提前准备，必须现场思考 |
| **诚实度扣分** | 强行堆砌无关技术栈直接扣分 |
| **架构分主导** | 即使代码完美但架构设计不合理，分数也不会高 |
