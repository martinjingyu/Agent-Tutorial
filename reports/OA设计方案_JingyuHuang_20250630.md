## 一、业务场景设计

### 推荐场景：多源情报融合的 Agent 工作流质量控制系统

候选人被要求为一个**多源情报融合分析系统**设计并实现 Agent 工作流质量控制的 Pipeline。系统需要从多个异构情报源（结构化日志、非结构化文档、实时消息流、历史数据库）中提取信息，经过多阶段 Agent 处理，最终生成一份**可验证、可追溯的情报分析报告**。

### 场景选择理由

| 维度 | 匹配度 | 理由 |
|------|:------:|------|
| **发挥 Agent 系统搭建强项** | ⭐⭐⭐⭐⭐ | Pipeline 修复直接对应 Linksome Agent 筛选流水线和 Agent-Tutorial Guardian-Worker 架构经验 |
| **暴露技术栈夸大风险** | ⭐⭐⭐⭐⭐ | GRPO/vLLM/DeepSpeed 在本题无自然落脚点，主动提及即暴露夸大 |
| **符合 JD 核心要求** | ⭐⭐⭐⭐⭐ | Agent 架构/工作流、知识检索增强、Agent Loop 优化、大模型级联全部覆盖 |
| **四不准三必须** | ✅ 完全合规 | 见下方详细检查 |

## 二、3道题详细设计

### Task 1（基础闭环）：Agent 工作流 Pipeline 修复与稳定性加固

#### 考察点
1. **错误处理与重试机制** — 对 LLM 调用失败（15% 模拟失败率 + 5% 非 JSON 返回）的容错处理，必须实现 try/except + 指数退避重试
2. **状态传递与 Pipeline 编排** — 4 个 Agent 步骤之间的结构化状态传递
3. **输出验证与 Schema 校验** — 每个步骤的输出必须经过格式校验
4. **运行稳定性** — 连续运行 5 次至少 4 次成功

#### 输入规范
一个 `source_materials.txt` 文件，包含 15 个来源的混合文本（约 20000 字）：

| 来源类型 | 数量 | 格式 | 内容说明 |
|---------|:----:|:----:|---------|
| 系统运行日志 | 6 条 | JSON Lines | 含 timestamp/level/module/message/request_id，2 条含错误堆栈 |
| 质量评估报告 | 1 份 | Markdown 表格 | 8 个质量指标及当前值/目标值/趋势 |
| 策略文档 | 4 份 | 编号文本 (POLICY_v1~v4) | v1 和 v3 对重试上限规定冲突（3次 vs 5次）；v2 和 v4 对超时阈值规定冲突（30s vs 60s） |
| 技术评审记录 | 1 份 | 对话文本 | 工程师对系统瓶颈的分析 |
| Slack 讨论 | 1 份 | 对话文本 | 产品经理和工程师对质量标准版本变更的讨论 |
| 产品路线图 | 1 份 | Markdown | 未审批的功能计划 |
| 客户反馈 | 1 份 | 邮件文本 | 客户对系统响应速度的投诉 |

#### 20000 字分层分配策略
| 层级 | 内容 | 字数 | 占比 |
|------|------|:----:|:----:|
| **核心层** | 系统运行日志(6条) + 质量评估报告(1份) | ~8000 | 40% |
| **冲突层** | 策略文档(4份) + 技术评审记录(1份) | ~6000 | 30% |
| **上下文层** | Slack 讨论 + 产品路线图 + 客户反馈 | ~4000 | 20% |
| **干扰层** | 冗余文档 + 无关日志 + 恶意输入线索 | ~2000 | 10% |

#### 输出规范
```python
def run_pipeline(source_materials_path: str) -> dict:
    """
    返回:
    {
        "final_report": str,          # 最终优化方案报告
        "processing_log": [...],       # 每次 LLM 调用的记录
        "evidence_state": {...}        # 证据状态
    }
    """
```

#### 噪声/干扰设计
- **策略版本冲突**：POLICY_v1 规定"重试上限 3 次"，POLICY_v3 规定"重试上限 5 次"
- **跨工单关联**：日志中 request_id "CUST-3381" 的超时错误与客户反馈邮件中的投诉对应同一用户
- **质量标准版本变更**：Slack 讨论中提到质量标准从 v2 升级到 v3，但质量报告仍引用 v2 标准
- **路线图未审批**：产品路线图中提到"Q3 接入 50 个新情报源"，但标注为"未审批"
- **冗余信息**：4 条策略文档中有 2 条内容完全重复（v2 和 v4 的"安全策略"部分相同）
- **缺失信息**：日志中有一条记录的 module 字段为空
- **Prompt Injection 线索**：Slack 讨论中提及用户输入导致系统输出异常

#### 脚手架代码故意缺陷（7个）

| # | 缺陷 | 预期修复 | 对应工程陷阱 |
|---|------|---------|------------|
| 1 | 无 try/except 的 LLM 调用 | 添加异常处理 + 指数退避重试 | 容错设计缺失 |
| 2 | 全局变量传递状态 | 函数参数传递 + 结构化状态对象 | 状态耦合 |
| 3 | 无输出校验 | Schema 校验 + 修复/重试 | 数据质量失控 |
| 4 | 硬编码配置 | 环境变量/配置文件 + 分层覆盖 | 环境耦合 |
| 5 | 使用 print() 代替 logging | 结构化日志 + 关键路径全覆盖 | 监控缺失 |
| 6 | 无输入清洗（直接拼接用户输入到 Prompt） | 输入清洗 + role 隔离 + 输出过滤 | 安全注入风险 |
| 7 | 无超时控制、无 Token 预算 | 设置 timeout + max_tokens + Token 计数器 | 资源失控 |

### Task 2（动态泛化）：Evidence State 中间表示设计与事实边界控制

#### 考察点
1. **信息建模与中间表示设计** — 设计 Evidence State 的数据结构
2. **事实边界控制** — 每个结论引用具体来源（source_id + line_number），不确定信息标注置信度，缺失信息标注"不知道"
3. **冲突检测与消歧** — 检测策略版本冲突并在报告中明确标注
4. **Schema 设计与扩展性** — 支持未来扩展到 50+ 情报源

#### 输入规范
- 复用 Task 1 的 `source_materials.txt`
- 一份 `schema_template.json`（故意设计得过于简单，仅包含 `{"source": str, "content": str}`）

#### 输出规范
- **文件 1**：`evidence_state_schema.json` — 完整的 JSON Schema 定义
- **文件 2**：`generate_evidence.py` — 从 `source_materials.txt` 生成 Evidence State 的代码

#### 验收标准
1. ✅ Schema 是合法的 JSON Schema
2. ✅ 代码能读取材料并输出符合 schema 的 Evidence State
3. ✅ 至少检测到 1 个策略版本冲突
4. ✅ 每个结论有至少 1 个来源引用（source_id + line_number）
5. ✅ 至少包含 1 个 `confidence < 1.0` 的结论
6. ✅ 至少包含 1 个 `status: "unknown"` 的条目
7. ✅ 包含 `requires_human_review` 字段（当冲突无法自动解决时标记）

### Task 3（极限压测 — 面试讨论）：Agent 工作流架构演进与极限压测

#### 考察点
1. **架构演进思维** — 从单体到分布式 Agent 网格的演进路径
2. **实时性理解** — 批处理 vs 流处理、增量计算/事件驱动
3. **技术选型判断** — 判断技术适用场景，诚实承认知识边界
4. **自进化深度** — Guardian-Worker 架构的触发条件与安全边界

#### 追问示例（10个）

| # | 追问 | 考察目标 |
|---|------|---------|
| 1 | 情报源从 6 个扩展到 50 个，数据类型从文本扩展到音视频，架构怎么变？ | 架构演进思维 |
| 2 | 实时性要求从 T+1 变为 T+0，你的 Pipeline 怎么调整？ | 实时性理解 |
| 3 | GRPO/vLLM/DeepSpeed 在这个场景中可以用在哪里？ | 技术栈诚实度 |
| 4 | vLLM Continuous Batching 在这个场景中是否适用？为什么？ | vLLM 理解深度 |
| 5 | GRPO 的 Group-Based Reward 机制能否用于优化 Pipeline 输出质量？ | GRPO 理解深度 |
| 6 | 自进化框架中，Guardian 如何区分临时故障和代码 Bug？如何自动修复？ | 自进化深度 |
| 7 | Agent 修改自己代码后引入新 Bug（如死循环），如何防止自我破坏？ | 元编程安全边界 |
| 8 | 你的 Pipeline 中 4 个 Agent 使用不同的 Prompt，如何支持中英文双语输出？ | Prompt 工程 |
| 9 | 50 个情报源下 LLM 调用次数可能从 10 次增长到 100+ 次，如何控制成本？ | 成本意识 |
| 10 | 什么情况下标记"需要人工审核"？阈值如何设定？ | 人机协作边界 |
