## 一、业务场景选择

**最终选定场景：智能安全审计与威胁情报分析系统**

### 场景描述
设计一个Agent系统，对大规模企业内部的**多源异构安全数据**进行自动化审计、威胁检测和报告生成。输入材料包括：
- 安全扫描报告（JSON/XML格式，含误报）
- 代码仓库commit日志（含安全修复记录）
- 第三方依赖清单（含已知CVE）
- 合规性检查表（SOC2标准，含规则冲突）
- 新型威胁情报报告（含未确认的新模式）
- 实时告警数据流（模拟Kafka流）

### 选择理由
| 候选人背景 | 场景映射 |
|---|---|
| LLM安全红队测试 | 安全审计天然是红队思维的延伸，候选人能快速理解业务 |
| Agent Pipeline搭建 | 需要设计"采集→分析→决策→上报"的完整Agent链路 |
| 自进化Agent框架 | 安全策略会过时，Agent需要根据新漏洞模式自我更新 |
| 噪声/冲突输入 | 安全策略文档之间常有矛盾，历史报告有误报，天然符合要求 |

## 二、三道题详细设计

### 第一题：基础闭环 — 「安全审计报告智能抽取与合规校验Agent」

**权重**：35%

#### 场景描述
> 你是一名安全运维工程师，每天需要处理来自不同工具的安全扫描报告、代码仓库的commit日志以及第三方依赖清单。你的任务是构建一个Agent系统，能够自动从这些异构数据中抽取关键安全信息，根据预定义的规则进行误报过滤，并生成一份结构化的合规审计报告。

#### 输入规范（4个文件）
1. **`scan_report.json`** — 安全扫描报告（15个finding，含3个误报埋点）
2. **`commits.csv`** — 20条commit记录（含安全相关和非安全相关）
3. **`dependencies.json`** — 第三方依赖清单（含已知CVE）
4. **`compliance_checklist.yaml`** — SOC2合规检查表

#### 输出规范
- **`audit_report.json`** — 结构化合规审计报告
- 字段完整性要求：所有预定义字段必须存在，缺失字段标记为null并说明原因
- 交叉验证正确性：commit日志中的修复信息必须与扫描报告中的漏洞正确关联
- 误报过滤准确率：至少正确识别2个误报（共埋了3个）

#### 考察点
| 维度 | 权重 | 说明 |
|---|---|---|
| Agent Pipeline完整性 | 25% | 数据摄取→清洗→抽取→关联→过滤→输出 |
| 结构化抽取准确性 | 20% | 字段完整性、格式规范、缺失值处理 |
| 规则引擎设计 | 20% | 可配置规则、热加载、优先级、冲突检测 |
| 跨源数据关联 | 20% | 精确+模糊匹配、多字段搜索、置信度评估 |
| 代码质量 | 15% | 模块化、错误处理、类型注解、日志 |

#### 噪声/干扰设计
| 噪声类型 | 具体设计 |
|---|---|
| 误报埋点 | 3个低危漏洞（CVSS<4.0，无PoC，前端组件） |
| 数据矛盾 | commit显示"已修复"但扫描仍标记为"open" |
| 缺失字段 | 部分finding缺少remediation字段 |
| 格式不一致 | 日期格式混用（ISO 8601 vs Unix timestamp） |
| 无关数据 | commit日志中包含大量非安全相关提交 |
| 重复数据 | 同一个CVE在不同扫描工具中出现两次 |
| 规则冲突 | 合规检查表中两条规则自相矛盾 |

#### 脚手架缺陷设计
1. **静默失败**：KeyError被except pass静默忽略，导致finding被丢弃
2. **精确匹配陷阱**：跨源关联只做大小写敏感的精确匹配
3. **硬编码规则路径**：规则文件路径硬编码，不可配置
4. **无状态管理**：每次运行从头处理，无缓存/增量机制
5. **同步阻塞**：所有步骤串行执行，无并发/异步设计

### 第二题：动态泛化 — 「自适应安全威胁图谱构建与多智能体协同分析系统」

**权重**：40%

#### 场景描述
> 你的安全审计Agent已经能处理已知类型的漏洞，但安全威胁在持续进化——新型攻击手法（如AI模型投毒、供应链依赖混淆、侧信道攻击）不断涌现。你需要将你的Agent升级为一个自进化系统：它能够自动发现未知的安全威胁维度，动态扩展数据抽取Schema，并通过多个专业Agent协作分析，最终将结果整合到一个知识图谱中。

#### 输入规范（在第一题基础上新增2个文件）
5. **`novel_threats.json`** — 新型威胁情报报告（含伪新模式、低置信度模式）
6. **`seed_graph.json`** — 知识图谱种子数据（含孤立节点、冗余边）

#### 输出规范
- **`extended_schema.json`** — 扩展后的数据抽取Schema
- **`collaboration_log.json`** — 多智能体协作日志
- **`knowledge_graph.json`** — 更新后的知识图谱
- **`evolution_report.md`** — 自进化过程报告

#### 考察点
| 维度 | 权重 | 说明 |
|---|---|---|
| 动态Schema扩展 | 20% | 版本管理、冲突检测、置信度评估、回滚机制 |
| 多智能体协作架构 | 25% | 角色定义、通信协议、共识机制、故障恢复 |
| Graph-based RAG | 25% | 图结构设计、路径分析、向量+图谱混合检索、增量更新 |
| 自进化机制 | 15% | 反馈驱动学习、置信度阈值、灾难性遗忘防护 |
| 系统可观测性 | 15% | 结构化日志、决策链路追踪、审计支持 |

#### 噪声/干扰设计
| 噪声类型 | 具体设计 |
|---|---|
| 伪新模式 | 看起来像新威胁，实为已知CVE变种 |
| 低置信度模式 | 证据极弱的新模式（如"量子解密攻击"） |
| Schema膨胀风险 | 连续输入3个弱相关新模式，测试收敛机制 |
| 孤立节点 | 知识图谱中存在无任何边连接的节点 |
| 冗余边 | 知识图谱中存在重复的边 |

#### 脚手架缺陷设计
1. **无Schema版本控制**：扩展Schema时直接覆盖，无版本历史
2. **Agent硬编码通信**：Agent之间通过全局变量通信，无消息格式定义
3. **无图更新机制**：知识图谱只读不写，无法增量更新
4. **无Agent故障恢复**：某个Agent崩溃后无重试/降级机制
5. **自进化无收敛**：无置信度阈值，所有新模式无脑加入

### 第三题：极限压测 — 「企业级安全审计数据流处理平台」

**权重**：25%

#### 场景描述
> 你的安全审计系统需要部署到真实企业环境——每秒处理数千条安全事件，数据来自多个异构源，且系统运行在资源受限的服务器上（4核8GB）。你需要设计一个高吞吐、低延迟的流式处理架构，支持优先级调度、优雅降级和实时监控。

#### 输入规范
- **10,000条消息流**（模拟Kafka），峰值500条/秒
- 消息格式：JSON，含event_id、source、timestamp、priority、data字段
- 优先级：1（紧急）到5（低优先级）
- 资源约束：单机4核8GB

#### 输出规范
- **`architecture_doc.md`** — 架构设计文档（含组件图、数据流图、部署拓扑）
- **`streaming_pipeline.py`** — 流式处理核心伪代码（50-100行）
- **`performance_report.json`** — 性能监控报告

#### 考察点
| 维度 | 权重 | 说明 |
|---|---|---|
| 流式处理架构 | 25% | 消息队列选型、消费者组、背压处理、窗口计算 |
| 优先级调度 | 20% | 优先级队列、抢占、老化、优先级反转防护 |
| 优雅降级策略 | 20% | 分级降级、触发条件、恢复条件、补偿机制 |
| 资源管理与监控 | 15% | 自适应限流、资源预算、预测性扩缩容 |
| 架构设计文档 | 20% | 架构图、关键设计决策、权衡分析、瓶颈分析 |

#### 噪声/干扰设计
| 噪声类型 | 具体设计 |
|---|---|
| 流量尖峰 | 第11秒突然飙升到500条/秒，持续10秒 |
| 低优先级洪流 | 大量Priority 5消息涌入，试图淹没系统 |
| 消息乱序 | 部分消息时间戳比前一条早 |
| 重复消息 | 约5%的消息是重复的（相同event_id） |
| 降级恢复一致性 | 降级期间丢弃的消息包含关键漏洞线索 |

#### 脚手架设计
- 提供最小脚手架：数据生成器 + Mermaid架构图模板
- 不提供完整代码实现
- 采用"架构设计文档 + 关键模块伪代码"模式

## 三、评分体系

### 总分分配
| 题目 | 权重 |
|---|---|
| 第一题「基础闭环」 | 35% |
| 第二题「动态泛化」 | 40% |
| 第三题「极限压测」 | 25% |

### 每道题评分方式
- 5个维度，每个维度0-10分
- 加权求和得到该题总分（满分100分）
- 最终总分 = 第一题×35% + 第二题×40% + 第三题×25%

### 分数线
| 分数区间 | 结论 |
|---|---|
| ≥80分 | Strong Hire（架构设计能力强，可直接进入终面） |
| 65-79分 | Hire（基本合格，需要面试进一步验证） |
| 50-64分 | Weak Hire（有潜力但差距明显，需谨慎） |
| <50分 | No Hire |

### 防灌水机制
1. **技术名词声明表**：候选人需如实标注GRPO/vLLM/DeepSpeed等使用情况
2. **追问验证清单**：面试时针对关键技术名词追问具体实现细节
3. **诚实加分项**：如实标注"理论了解"且代码中未过度使用 → +3分
4. **架构分占主导**：架构设计占60%，代码实现占40%

### 评分流程
```
候选人提交OA → 两位面试官背对背独立评分
    → 差异>15分？讨论对齐 → 最终评分
    → 差异≤15分？取平均
    → 面试追问验证 → 调整评分（±5分）
    → 输出最终评分卡
```

## 四、噪声材料总量规划

| 文件 | 字数 | 噪声占比 |
|---|---|---|
| scan_report.json | ~3000字 | ~600字（20%） |
| commits.csv | ~2000字 | ~400字（20%） |
| dependencies.json | ~1000字 | ~200字（20%） |
| compliance_checklist.yaml | ~1000字 | ~200字（20%） |
| novel_threats.json | ~4000字 | ~800字（20%） |
| seed_graph.json | ~2000字 | ~400字（20%） |
| 实时数据流 | ~3000字 | ~600字（20%） |
| 场景说明文档 | ~4000字 | ~0字 |
| **总计** | **~20000字** | **~3200字（16%）** |

### 噪声设计原则
1. **不设无解的死局**：每个噪声都有至少一种合理的解决路径
2. **不设"猜出题人意图"的陷阱**：解决路径是工程常识
3. **不设时间陷阱**：不会因未发现某个噪声导致系统崩溃
4. **噪声密度合理**：16%的噪声占比，不会让候选人觉得数据全是垃圾

## 五、关键设计决策记录

| 决策项 | 选择 | 理由 |
|---|---|---|
| 业务场景 | 安全审计 | 与候选人红队背景衔接，自然引出Agent架构 |
| 三段式演进 | 基础→泛化→压测 | 难度递进合理，覆盖JD所有要求 |
| 第二题权重最高 | 40% | 最贴近JD要求（多智能体协作+Graph RAG+自进化） |
| 第三题采用伪代码 | 架构文档+伪代码 | 避免代码量过大导致无法完成 |
| 防灌水策略 | 声明表+追问+诚实加分 | 多维度验证，不给灌水空间 |
| 评分流程 | 双人背对背 | 减少主观偏差 |

## 六、面试追问清单

如果候选人OA得分在边界线（50-70分），面试时重点追问：

| 技术名词 | 追问问题 | 验证标准 |
