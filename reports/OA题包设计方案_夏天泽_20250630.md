## 一、业务场景设计

### 场景名称：多源信息融合的幻觉检测与自适应修复 Pipeline

**场景描述**：设计一个多阶段Pipeline，接收来自多个异构情报源（结构化JSON、半结构化Markdown、非结构化纯文本）的文本片段，系统需要：
1. **解析与抽取** — 对不同格式的源文档进行统一解析，抽取预定义的实体信息
2. **跨源冲突检测** — 检测同一实体在不同源中的属性冲突（即信息层面的"幻觉"）
3. **定向修复** — 根据检测结果对冲突属性做最小化定向修复
4. **质量报告** — 输出可信度标注的结构化知识图谱

### 为什么这个场景适合夏天泽

| 候选人优势 | 场景映射 | 考察维度 |
|-----------|---------|---------|
| SHARP（EMNLP 2025）— 定位问题神经元 | detect()节点定位冲突实体和属性 | 质量闭环与定向修复 |
| D²HScore — 语义广度与深度分析 | 跨源可信度双维度评分 | 输入建模与边界控制 |
| 类脑记忆架构（毕业论文） | PipelineState状态设计与版本管理 | 动态拆解与状态传递 |

### 符合"四不准三必须"

- ✅ 不准纯算法题 — 核心是Pipeline编排和状态设计
- ✅ 不准Prompt语法调优题 — LLM只是工具，架构是核心
- ✅ 不准依赖特定框架 — 纯Python实现，无LangChain/CrewAI
- ✅ 不准限定唯一解题路线 — 状态结构、节点分工、修复策略均可自由设计
- ✅ 有复杂业务目标与噪声输入 — 多源异构文本+格式污染+语义冲突
- ✅ 有可量化输出目标 — 事实准确率、冲突检出率、修复成功率
- ✅ 有极大容错空间 — 检测可以漏报，修复可以部分成功

## 二、三段式题目详细设计

### 第一段：已知维度抽取（30分）— "基础抽取引擎"

**题目**：给定3-5个结构化程度不同的情报源（1个JSON、1个Markdown、1个纯文本），实现Pipeline从每个源中抽取预定义的实体类型（人物、组织、事件、时间）。

**考察点**：
- **输入建模**：为不同源设计统一的 `SourceSchema`，处理格式差异和编码问题
- **动态拆解**：将任务拆解为 `parse → extract → normalize` 三个子步骤
- **状态传递**：设计 `PipelineState` 中间结构，包含 `raw_sources`, `parsed_docs`, `extracted_entities`
- **边界控制**：处理空源、格式异常、超长文本截断

**输入**：`data/sources/` 目录下的3-5个文件（不同格式）
**输出**：`output_stage1.json` — 结构化实体列表，每个实体标注来源和原始文本引用
**时间分配**：45分钟

### 第二段：未知维度自适应（40分）— "跨源冲突检测与修复"

**题目**：在第一段基础上，新增第4-5个情报源（故意包含与已有信息矛盾的内容）。候选人需要：
1. 检测跨源冲突（同一实体在不同源中的属性不一致）
2. 设计可信度评估机制（哪个源更可靠？）
3. 实现定向修复策略（只修复冲突属性，保留正确内容）

**考察点**：
- **质量闭环**：检测→定位→修复的完整闭环
- **定向修复**：不是全局重写，而是精确定位冲突属性做增量修复
- **状态传递升级**：Stage 1的 `PipelineState` → Stage 2增加 `conflicts`, `resolution_attempts`, `confidence` 字段

**输入**：`data/sources/` 新增2个冲突源 + Stage 1的输出
**输出**：`output_stage2.json` — 包含 `conflicts_detected`, `fix_applied`, `remaining_ambiguities`
**时间分配**：45分钟

### 第三段：海量异构文本对齐（30分，面试讨论）— "架构设计答辩"

**面试追问方向**：
1. **扩展性**：如果情报源从5个扩展到5000个，你的Pipeline架构需要做什么改变？（流式处理、分片、异步编排）
2. **记忆管理**：你的类脑双周期记忆架构如何映射到这个Pipeline的长期知识库设计？（验证简历声称的架构）
3. **元错误**：你的检测节点如果本身产生了误判，Pipeline如何发现和纠正？
4. **修复策略的trade-off**：定向修复和全局重写的边界在哪里？什么情况下应该选择重写而非修复？

**时间分配**：30分钟面试讨论

## 四、脚手架代码的故意缺陷设计（10个）

### 缺陷清单

| ID | 位置 | 缺陷类型 | 具体表现 | 预期修复方式 | 考察维度 |
|:---|:---|:---|:---|:---|:---|
| **D1** | `main.py` `run_pipeline()` | **状态丢失** | Pipeline节点间没有状态传递，每个节点独立处理原始输入 | 设计统一的 `PipelineState` 数据结构 | 动态拆解与状态传递 |
| **D2** | `detector.py` `detect()` | **错误处理缺失** | `call_llm()` 没有try/except，API异常时整个Pipeline崩溃 | 添加try/except+指数退避重试+降级策略 | 质量闭环 |
| **D3** | `detector.py` `detect()` | **边界条件** | 空证据时返回 `{"hallucination": False, "confidence": 1.0}`（认为无证据=无幻觉） | 检测空证据，标记为"无依据回答" | 输入建模与边界控制 |
| **D4** | `extractor.py` `extract()` | **状态丢失** | 同一实体在多个源中出现时被抽取多次，无去重 | 实现实体归一化：统一命名、合并同实体 | 动态拆解与状态传递 |
| **D5** | `detector.py` `detect()` | **逻辑错误** | 只输出全局 `{"has_conflict": True/False}`，未定位到具体冲突实体和属性 | 输出结构化检测结果（实体级粒度） | 质量闭环与定向修复 |
| **D6** | `detector.py` `detect()` | **边界条件** | 单源实体默认标记为"可信"，但该源可能是虚假信息源 | 实现单源可信度衰减 | 输入建模与边界控制 |
| **D7** | `resolver.py` `resolve()` | **逻辑错误** | 全局重写整个实体而非定向修复冲突属性 | 实现定向修复：只修改冲突属性 | 质量闭环与定向修复 |
| **D8** | `resolver.py` `resolve()` | **错误处理缺失** | 无最大修复次数限制，可能陷入无限循环 | 添加最大修复次数限制（如3次），超过标记为"需人工审核" | 质量闭环 |
| **D9** | `models.py` `PipelineState` | **状态丢失** | 缺少 `confidence` 和 `provenance` 字段 | 增加置信度和证据链字段 | 动态拆解与状态传递 |
| **D10** | `config.py` | **边界条件** | API key和路径硬编码，无环境变量读取机制 | 使用 `os.environ.get()` 读取，路径不存在时抛出明确错误 | 输入建模与边界控制 |

### 缺陷连锁依赖关系

```
D1(无状态传递) ──→ 候选人必须设计 PipelineState
                    │
D4(无实体去重) ────→ 如果只修了 D1 没修 D4 → 状态设计不完整
D9(无confidence) ──→ 如果修了 D1+D4 没修 D9 → 状态设计缺乏深度
                    │
D5(检测粒度太粗) ──→ 如果修了 D1 没修 D5 → 状态传递了但内容无用
                    │
D7(全局重写) ──────→ 如果修了 D5 没修 D7 → 检测精细了但修复粗暴
D8(无限循环) ──────→ 如果修了 D7 没修 D8 → 定向修复了但可能死循环
```

## 六、针对候选人特点的出题策略

### 三道防线：防止候选人用LLM知识绕过去

**防线1：脚手架强制Pipeline结构**
脚手架代码已给出五个节点的空壳函数和明确接口签名，候选人必须在框架内工作：
```python
def parse(state: PipelineState) -> PipelineState: ...
def extract(state: PipelineState) -> PipelineState: ...
def detect(state: PipelineState) -> PipelineState: ...
def resolve(state: PipelineState) -> PipelineState: ...
def report(state: PipelineState) -> PipelineState: ...
```
每个节点必须有实质性逻辑，空函数扣分。

**防线2：缺陷D7（全局重写）的陷阱**
全局重写会引入新幻觉且无审计轨迹。只有实现定向修复（根据detection_result中的具体冲突属性做最小化修改）才能拿高分。

**防线3：第三段面试追问的"元错误"问题**
> "你的幻觉检测节点如果本身产生了误判，你的Pipeline如何发现和纠正？"
直接打击"依赖LLM检测LLM"的循环困境。

### 让幻觉检测背景成为解题优势

**优势转化路径**：
- SHARP（定位问题神经元）→ detect()节点中定位冲突实体和属性
- D²HScore（语义广度与深度分析）→ 跨源可信度双维度评分

**加分项**：
- 将SHARP的"激活概率熵"思路转化为"实体属性冲突的置信度评分"：+2分
- 实现双维度可信度评分（信息广度×信息深度）：+2分

### 反制"一个巨大Prompt"策略

1. **节点独立运行要求**：每个节点可独立测试，耦合度过高扣分
2. **结构化状态传递要求**：禁止把所有信息塞进一个 `raw_llm_output` 字段
3. **定向修复要求**：全局重写无法通过D7的修复验证
