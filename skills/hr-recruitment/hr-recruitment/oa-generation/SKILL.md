# OA Generation Skill

## 输入
- JD 文件路径
- 候选人 profile（stage1_report.md）
- OA 设计要求文档
- 会议讨论确定的题目方案

## 输出目录结构
所有文件输出到 `candidates/{候选人姓名}/OA_v3/` 目录下：

```
OA_v3/
├── README.md              # 题目说明（候选人视角）
├── CONTEXT.md             # 设计上下文（面试官视角）
├── DELIVERABLES.md        # 交付物清单
├── materials/             # 输入材料
│   ├── contract_A.md      # 合同A（含噪声）
│   ├── contract_B.md      # 合同B（含噪声）
│   ├── contract_C.md      # 合同C（含噪声）
│   ├── compliance_rules.json  # 合规知识库
│   └── reference_output.json  # 参考输出模板
├── scaffold/              # 代码框架（只给工具，不给思路）
│   ├── __init__.py
│   ├── config.py
│   ├── llm_client.py
│   ├── pipeline.py
│   ├── validator.py
│   └── utils.py
├── SCORING.md             # 评分标准
├── tests/                 # 测试文件
│   ├── sample_output.json
│   └── qa_baseline.py
└── INTERNAL_EVALUATION.md # 内部评估
```

## 生成步骤

### Step 1: 读取输入
- 读取 JD、候选人 profile、OA 设计要求、会议结论

### Step 2: 设计题目方案
- 基于会议结论确定题目名称、业务场景、输入材料、输出要求、评分维度
- 确保三段式递进设计（基础闭环→动态泛化→极限压测）

### Step 3: 生成题目说明文件
- README.md: 候选人视角的题目说明
- CONTEXT.md: 面试官视角的设计上下文
- DELIVERABLES.md: 交付物清单

### Step 4: 生成输入材料
- materials/ 目录下的合同文件、合规规则库、参考输出模板
- 合同需包含设计好的噪声类型（OCR错误、扫描倾斜、水印覆盖、手写批注、LLM特有噪声）

### Step 5: 生成代码框架
- scaffold/ 目录下的 Python 框架代码
- **只给工具，不给思路**：提供 LLM 客户端、基础工具函数，但不暗示 Pipeline 结构
- 代码框架中故意植入可控缺陷（如无超时/重试、配置硬编码、无校验等），用于评分

### Step 6: 生成评分标准
- SCORING.md: 五维度评分细则 + 三段式评分表

### Step 7: 生成测试文件
- tests/sample_output.json: 完整预期输出示例
- tests/qa_baseline.py: 自动化检查脚本

### Step 8: 生成内部评估
- INTERNAL_EVALUATION.md: 面试官操作指南 + 题目定位 + 考察目标矩阵

### Step 9: 最终审查闭环
- 审查所有生成的文件
- 发现缺陷 → 修改 → 再确认
- 输出 review_report.md

## README.md 写作规范（重要！）

README.md 是候选人看到的唯一题目说明，必须做到：

### 1. 结构要求
- **一句话总结**：开头用一句话说清楚"你要做什么"
- **背景故事**：用业务场景引入，让候选人理解"为什么做这个"
- **输入输出**：清晰列出输入文件、输出格式
- **分步任务**：用"第一步/第二步/第三步"代替"Level 1/2/3"，每步有明确的"做到什么程度算完成"清单
- **交付物**：列出必须交的文件，区分核心和辅助
- **评分标准**：用大白话解释每个维度，避免"动态拆解与状态传递"这类术语
- **常见坑**：列出候选人最容易犯的错误

### 2. 语言要求
- **口语化**：像人在说话，不是文档在说话。用"你要"、"你的任务"、"简单说就是"
- **具体化**：不说"处理噪声"，说"合同里有 OCR 错字'confldentlal'，你怎么处理？"
- **少用术语**：避免"中间表示"、"状态传递"、"输入建模"等抽象词
- **中英双语**：关键术语保留英文，解释用中文

### 3. 每步任务的要求
每个 Level/Step 必须包含：
- **目标**：一句话说清这一步要做什么
- **具体要求**：3-5 条具体的技术要求
- **完成标准**：用 ✅ 清单列出"做到什么程度算完成"
- **不要求**：明确告诉候选人这一步不需要做什么（降低焦虑）

### 4. 反面教材（不要这样写）
```
❌ Level 1：基础闭环（40分）
   要求：基本的 LLM 调用编排，简单的输入清洗
```
→ 候选人看完不知道具体要做什么

```
✅ 第一步：跑通基础流程（40分 | 建议45分钟）
   目标：选一份最简单的合同，跑通"读取→提取→对齐→输出"全流程
   具体要求：
   - 调用 LLM 提取合同中的关键条款
   - 跟合规规则做比对，输出 JSON 报告
   - 做基本的文本清洗
   完成标准：
   ✅ 程序能跑，输出合法的 JSON
   ✅ JSON 里有至少 5 条提取的条款
   ✅ JSON 里有至少 3 条对齐结果
   这一步不要求：分块、自纠正、回译验证
```

### 5. 交付物清单的要求
- 区分"核心交付（必须交）"和"加分项（可选）"
- 核心交付控制在 5-7 个文件以内
- 每个文件用一句话说明"是什么"

### 6. 评分标准的要求
- 每个维度用"简单说就是"加一句大白话解释
- 等级划分给出"典型表现"而非抽象描述
- 示例：
  ```
  | Strong Pass | ≥ 80 | 一眼看出 LLM 会在哪里翻车，提前设计了预防和修复机制 |
  | Pass | 60-79 | 做了步骤拆分，但步骤之间各干各的，没有形成闭环 |
  ```

## 约束
- 不准暗示 Pipeline 结构或解题思路
- 不准把题目变成算法题或 Prompt 调优题
- 输入材料必须包含足够的噪声和冲突
- 输出要求必须可量化、可自动评分
- 评分必须压在 Pipeline 设计直觉上，而非代码完美度
