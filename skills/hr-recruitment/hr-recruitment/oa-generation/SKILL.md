# OA Generation Skill

## 核心原则

### 1. 每道题都应该是独一无二的
- 题目场景、输入材料、考察角度必须根据候选人背景定制
- 利用候选人的独特经历（如某篇论文、某个项目）设计差异化考点
- 避免"换个名字就能给另一个人用"的通用题目

### 2. 考察的是 Pipeline 设计直觉，不是代码熟练度
- 核心：候选人能否针对 LLM 的天然缺陷（幻觉、格式漂移、缺乏全局观）设计可控的 Pipeline
- 不考算法竞赛题、不考 Prompt 调优、不考框架 API 记忆
- 代码只是表达设计的载体，设计本身才是评分重点

### 3. 题目要有递进层次
- 从简单到复杂，从单一到综合
- 每一层在前一层基础上增加新的约束或挑战
- 让不同水平的候选人都有展示空间

### 4. 原创性 > 标准化
- 不要套用固定场景（如总是"合同审查"）
- 根据候选人背景选择匹配的业务场景
- 输入材料中的噪声、冲突、陷阱要精心设计，有明确的考察意图

### 5. 严格控制时间和输入输出量
- 总时长严格控制在 2 小时以内
- **输入材料总字数统一控制在 8000-15000 字量级**（所有场景均适用）。这是为了让候选人在有限时间内面对足够复杂的信息量，考察其信息筛选和 Pipeline 设计能力。
  - **设计文档中必须明确标注输入材料总字数**，并确保所有输出文件（README、EVALUATION、scaffold 等）中的字数描述一致
- 输出不设字数下限——题目本身的复杂度自然要求候选人进行多次 API 调用和足够的生成文本，无需人为设限
- 规定使用的模型（如统一用 gpt-4o-mini 或本地模型），避免候选人依赖模型能力差异

### 6. 防止 Vibe Coding
- 明确限制每阶段输出的代码/文本量（如"核心逻辑不超过 200 行"或"用伪代码/流程图+关键代码片段"）
- 要求候选人在代码中写注释说明设计决策理由
- 评分时重点看设计文档/流程图/决策说明，而非代码量
- 可要求候选人先写设计思路（200字以内），再写代码

### 7. 对基础一般的候选人友好，但保留高分空间
- 第一阶段应足够简单，让只懂 Python 基础的人也能上手
- 高分需要通过 high-level thinking 来拉开差距，而非写复杂代码
- 允许用伪代码、流程图、文字描述来替代部分实现
- 评分权重向设计决策倾斜（>50%），代码实现占小头

## 生成流程

### Phase A: 理解输入
- 阅读 JD，提取核心能力要求
- 阅读候选人 profile，找出可用的背景素材（论文、项目、技能）
- 阅读 OA 设计要求，理解招聘画像
- 如果有会议结论，作为设计起点

### Phase B: 设计题目方案（输出设计文档）
- 确定业务场景（与候选人背景相关、能自然引出 Pipeline 设计）
- 设计三段式递进任务（基础闭环 → 复杂泛化 → 极限压测）
- 设计输入材料中的噪声/冲突/陷阱类型
- 确定输出格式和评分维度
- 确保题目"不是刷题能过的"——需要真正的设计思考
- **量化所有约束**：
  - 输入材料总字数：统一 **8000-15000 字**量级（所有场景均适用）
  - 每阶段输出格式（不设字数下限——题目复杂度自然要求足够的 API 调用和生成文本）
  - 规定使用的模型（如统一使用 gpt-4o-mini，API key 由题目提供）
  - 代码量限制（如核心 Pipeline 逻辑 ≤ 150 行 Python）
  - 时间分配建议（如阶段一 45min、阶段二 45min、阶段三 30min）
  - **⚠️ 字数决策必须传播到所有输出文件**：设计文档中确定的字数范围，必须在 README.md、EVALUATION.md、scaffold/input.md 等所有文件中保持一致。审查阶段（Phase D）需专门检查此项一致性。

### Phase C: 生成题目包

**Step C1: 先生成一份设计文档**，作为后续所有输出文件的单一设计真相源。设计文档记录 Phase B 的设计决策，确保所有下游文件（README、输入材料、代码框架、评分标准、评估文档等）基于同一套设计约束生成，避免各文件之间的不一致。

**Step C2: 基于设计文档生成题目包输出文件**
- 候选人视角的题目说明（README 或类似）
- 面试官视角的设计上下文
- 输入材料（含精心设计的噪声和冲突，严格控制总字数）
- 代码框架（只给工具，不给思路，可植入可控缺陷）
- 评分标准
- 测试/验证文件
- 内部评估文档

### Phase D: 最终审查闭环
- 审查所有生成的文件
- **一致性检查（关键）**：
  - 输入材料字数：设计文档中标注的字数 vs 实际 input.md 字数是否一致（统一标准 8000-15000 字）
  - 所有文件中的字数/时间/模型描述是否统一（README、EVALUATION、scaffold 等）
  - 如果设计文档写的是"8000-15000 字"，但某处仍出现"800 字"或"≤2000 字"等旧描述，必须修正
- 发现缺陷 → 修改 → 再确认
- 输出审查报告

## 输出位置
- 输出到 `candidates/{候选人姓名}/OA/` 目录下
- 如果该目录已存在，自动加版本后缀 `_v2`、`_v3` 等

## 质量要求

### 题目说明（候选人视角）
- 开头一句话说清"你要做什么"
- 用业务场景引入，让候选人理解上下文
- 清晰列出输入输出
- 分步任务有明确的完成标准
- 用口语化语言，像人在说话
- 列出常见坑
- **明确标注**：总时长、建议时间分配、使用模型、输出格式和字数限制

### 输入材料
- 包含足够的不确定性和噪声
- 噪声要有设计意图（考察什么能力）
- 可包含：格式混乱、信息缺失、矛盾冲突、无关干扰等
- **严格控制总字数**：所有场景统一控制在 **8000-15000 字**量级。这是为了让候选人在有限时间内面对足够复杂的信息量，考察其信息筛选和 Pipeline 设计能力。
  - **设计文档中必须明确标注输入材料总字数**，并确保所有输出文件中的字数描述一致
- 陷阱数量适中：建议总共 4-6 处陷阱（而非 10+），2 小时内能合理处理

### 代码框架
- 只提供基础工具函数（LLM 客户端、文件读写等）
- 不暗示 Pipeline 结构或解题思路
- 可故意植入可控缺陷（如无超时、无校验、配置硬编码等）
- **代码量限制**：框架本身 ≤ 50 行，候选人需补充的核心逻辑建议 ≤ 150 行

### 评分标准
- 评分维度反映核心考察目标
- 等级划分有明确的典型表现描述
- 可量化、可操作
- 明确区分"基础分"（完成功能）和"高分"（设计优雅）
- 评分维度应覆盖多个方面（如架构设计、缺陷控制、代码质量、反思深度等），不预设固定权重比例
- 每个 OA 题目的评分维度权重应根据题目特点灵活设计，核心原则是"设计直觉 > 代码量"

### 内部评估
- 题目定位和设计策略说明
- 面试官操作指南
- 红线行为（直接 FAIL 的标准）
- 面试追问建议
- **预期答案示例**：给出 2-3 种不同水平的典型答案描述（差/中/好）

## 约束
- 不准暗示 Pipeline 结构或解题思路
- 不准把题目变成算法题或 Prompt 调优题
- 输出要求必须可量化、可评估
- 评分必须压在 Pipeline 设计直觉上，而非代码完美度
- 每次生成的题目应在场景、材料、考察角度上有明显差异
- **必须量化输入输出**：每份输入材料标注字数，每阶段输出标注字数/行数限制
- **必须规定使用模型**：统一指定模型，避免模型能力差异影响公平性
- **必须防 Vibe Coding**：限制代码量，要求设计说明优先
- **必须对基础一般者友好**：第一阶段应简单到"只懂 Python 基础也能做"
